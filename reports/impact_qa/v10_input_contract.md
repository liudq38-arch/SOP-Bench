## 1. 必须补入的输入

生成器接收完整、按型号和拆装方向区分的 `procedure`，其中有全体步骤、正常结果、必要先后关系及可选分支；再接收当前动作和上下文。完整指覆盖声明的流程范围，不指强制一个总排序。缺失的规范须显式标 unknown，不能由一条正常演示补成确定规则。

```json
{
  "task": {"name": "angle grinder", "variant": "source-verified model", "workflow": "assemble"},
  "procedure": {
    "procedure_id": "versioned-reference",
    "coverage": "partial",
    "procedure_text": "Full supplied normal procedure, not a narration of this trial",
    "steps": [],
    "prerequisites": [],
    "state_mappings": [],
    "source_catalog": []
  },
  "target": {"event_id": "...", "step_id": "...", "component_id": "...", "receiver_id": null, "hand": "right", "view": "ego", "start_s": 0, "end_s": 1},
  "reference_annotations": [],
  "component_states": [],
  "observed_events": [],
  "visual_facts": [],
  "coverage": {"history_until_target": "unknown", "initial_state": "unknown", "cross_view_sync": "unverified"},
  "evidence_catalog": [],
  "selected_intents": []
}
```

以上是字段示意，省略号和时间值不是实际样本。每条输入事实都有稳定 id、源文件和 JSON/CSV 定位、时刻/区间、视角、来源类型。状态记录给 component_id、before/after、valid_from/valid_to；发生事件给 attempt_id、start/end、所改变的状态和证据。图边给 before/after、AND/OR/condition、authority、source_ids。别名映射、视角同步和状态实例映射有独立验证状态。

## 2. 题型与选择

| 题型 | 典型问法（示意） | 所需证据 |
|---|---|---|
| 安装对象/接收部件 | 我是否把 X 正确安装到 Y 上？ | X/Y 关系及对应完成状态；规范映射要与型号匹配 |
| 动作完成 | 到片段结束时，我完成 X 的安装了吗？ | 安装事件或终态；区分片段前已经安装和片段内完成 |
| 当前安装状态 | 此时 X 是否安装正确？ | 同一时刻的组件状态；无需伪造片段内安装动作 |
| 实际顺序 | 在安装 B 前，我做了什么？ | 实际事件时间线，完整覆盖被问的两个事件 |
| 规范顺序 | 我是否先完成 A 再安装 B，顺序正确吗？ | A→B 适用规范与实际时间/状态；非单条视频的顺序频率 |
| 漏步 | 在安装 B 前，我漏掉必要步骤了吗？ | 必做前置、初态、截至 B 的完整相关历史；排除已满足/可选步骤 |
| 多余操作 | 安装过程中是否做了不必要的拆卸？ | 多余标签或适用规范；不能把返工和合法重试都算多余 |
| 错误与纠正 | 安装哪里出错？我采取了什么纠正操作？ | 错误标注/规则违例与实际动作；成功恢复另外需要结果 |
| 工具/位置/方法 | 我用了什么工具、安装在哪里、怎样连接？ | 原对象/关系/视觉信息；正确工具和正确位置要有规范来源 |

先根据证据选题型，再写问句；每事件通常 2 题，不强凑。安装事件优先“安装关系或完成”，第二题选有证据的顺序、错误、纠正或操作细节。允许正常段和错误前提反问，不能用 phase 直接确定 Yes/No。不在本轮强行固定百分比：先按数据支持报告每种题的可生成覆盖率。Assembly101 语料的完成/漏步题存在单一答案偏向，不照搬这种偏差。

## 3. 流水线与职责

1. `procedure.txt` 整理完整规范文本、步骤图及来源；有资格的边用于规范判断，挖掘边只作候选和检索线索。编译器输出后由代码验证引用、条件和图一致性。
2. 组装目标动作、部件—接收部件关系、ASR/PSR 状态/事件及真实时间轴。按问题扩充目标前后状态帧或历史片段；不能把所有顺序题都限制为当前 16 帧或固定 ±3 秒。
3. `plan.txt` 根据证据选出最多两个互补题型，并输出待补证据。较短的当前微动作段若不足以判断安装结果，就转为粗步骤/完成事件窗口。
4. `generate.txt` 生成短问答与逐声明来源，保留安装、完成、顺序、遗漏的能力。
5. 代码检查来源 id、映射、时间覆盖和允许的规范边；代码计算前置关系、状态变化和时间，模型负责自然语言表达。
6. `review.txt` 分别判断来源支持和视频可见性。来源已支持但视频不清楚时为 needs_evidence；不再一律以“视频无法独立证明规范”拒绝题目，也不因此放过虚构物理原因。

生成与评测字段分离：写参考答案可见真实 phase、异常类型、ASR/PSR 真值、错误描述；被测模型输入可包含公开正常 procedure/图、问题、指定视频及协议允许的历史，不包含参考答案、测试执行的真值状态和错误标签。规范图如果用于评测，必须在测试之外固定，不能从测试执行挖掘后又评估其顺序理解。跨镜头真值转移需要核实同步，或先以 front 视角建立完成/状态 QA。
