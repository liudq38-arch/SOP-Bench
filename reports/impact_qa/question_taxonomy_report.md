# EgoErrorVQA 开放题问法、Assembly101 分布与 IMPACT v10 设计

核查：2026-09-18。结论：安装到指定部件、安装/步骤是否完成、实际先后顺序、规范顺序、漏步和多余操作均属于参照语料的真实题型。先前只围绕局部手部动作的 v7，以及侧重阶段/异常的 v8/v9，未充分覆盖这类问题。v10 必须恢复完整 procedure 输入，并按证据选择安装/完成/顺序题。

## 1. 来源与统计口径

使用 EgoErrorVQA 官方提交 `5403cdd05e007b01c88448587c1a1803a27266e2` 的四份开放题 JSON，本地文件此前已对 Git blob 和长度核验。总计 1805 片段、3560 QA，规范化空白及大小写后有 1747 个唯一问句。本报告统计全部发布题，不只挑示例。

| 来源 | 片段 | QA | 唯一问句 |
|---|---:|---:|---:|
| CC4D | 960 | 1857 | 1143 |
| Assembly101 | 446 | 859 | 352 |
| EgoOops | 215 | 418 | 147 |
| EPIC-Tent | 184 | 426 | 105 |

每片段题数为 1 题 123 段、2 题 1609 段、3 题 73 段。重复问句用于不同视频不能简单删除，但统计问法多样性时必须另外报唯一问句。

作者没有公开逐 QA 的语义题型编码。以下句式为直接文本统计，主题为公开正则的非互斥特征统计，既非作者官方题型分布，也非全量人工语义标注。一个问题可以同时涉及安装、状态和顺序，因此主题比例不加总为 100%。所有逐题命中、规则、原文和索引均保留在 [summary.json](question_taxonomy/summary.json)、[all_qa_coded.jsonl](question_taxonomy/all_qa_coded.jsonl)、[实例索引](question_taxonomy/examples.json)。

## 2. 开放式不等于只问 What/Why

3560 对中，2163 题以 Did/Is/Have 等助动词起首，为判断式问句（60.76%）；What 1325（37.22%）；Why 66（1.85%）；How 1（0.03%）；其他 5（0.14%）。Assembly101 的判断式为 707/859（82.31%），What 133，Why 19。答案是自由文本，通常在 Yes/No 后解释动作或错误；这仍是 open-ended QA，并非 MCQ。

整体答案起首 Yes=1524、No=637、其他=1399。正常来源也有 272 个 No，错误来源也有 61 个 Yes。例如正常段的“我漏步了吗？”答案 No；错误段的“我顺序做错了吗？”答案 Yes。生成时必须按问题命题确定极性，不能把正常强制写成 Yes、异常强制写成 No。

| 错在哪里、原因、应该怎样等解释式措辞 | 424，11.91% | 95，11.06% |

| 时间/温度词 | 207，5.81% | 0 |
| 明确位置/朝向/对齐词 | 212，5.96% | 94，10.94% |

这些列是可复核的文字特征，不代表未命中就不涉及该主题。尤其“哪里出错了？”可能在答案解释顺序，故不能宣称 Assembly101 只有 9 道顺序理解题。其源错误备注包含 wrong order 或 previous mistake 的共有 **22 片段、44 QA**；答案含顺序/前后词有 31 QA，也仍不是完整人工语义计数。before/after 在烹饪问句中常仅定位上下文，不能全部算成规范顺序判断。

代表问法，以下中文为原题释义；每项给出本地数据索引以便查看原文，不是假设 IMPACT 已有对应真值：

- 安装关系：“我是否把长方形车身正确连接到底盘上？”——Assembly101:1:0，答案确认连接状态。
- 完成：“我是否完整完成了把连接件装到底盘上的过程？”——Assembly101:3:1。
- 漏步：“把车轮装到底盘时，我漏掉步骤了吗？”——原例及所有命中见 examples.json 的 omission。
- 多余：“把保险杠装到驾驶室时，我做了多余步骤吗？”——unnecessary_action 例。
- 顺序错误：“我把底座连接到底盘的顺序错了吗？”——explicit_order_sequence 例。
- 错误解释：“尝试把车身装到底盘时哪里出错？”——源备注 wrong order，答案解释乱序；该问句本身不含 order。
- 纠正：“我为什么要把车身从底盘上拆下？”——源 correction，答案说明在修正之前的错误。
- 操作方式：“我做了什么来把驾驶室和内部件装在一起？”——同一操作的确认题/叙述题可以组成两题，但避免只做无信息量同义改写。

Assembly101 来源分布：correct 341 片段/678 QA，mistake 77/153，correction 28/28。文本命中的 68 道明确完成题全部来自 correct 且回答 Yes；70 道遗漏题和 81 道多余题全部来自 correct 且回答 No。这是发布子集的明显问法—答案偏向，不适合作为新数据必须复刻的比例。新 IMPACT 可以用真实未装/错装状态补足否定完成题，但不得为平衡而制造错误。

## 4. Assembly101 与 EgoErrorVQA 到底给了什么输入

Assembly101 原始 mistake 标注含 `verb`、两个工作对象、正确/错误/纠正、错误备注。这使“把 X 安装到 Y”有明确的两对象来源。官方 README 对错误备注的短证据是 “the two parts are not attached at their correct position”。[原标注说明](https://github.com/assembly-101/assembly101-mistake-detection)

EgoErrorVQA 发布的 Assembly101 行保留 `verb, first_object, second_object, error_label, error_annotation`；`task_id=toy car assembly` 对应 procedure.json 的程序文本。生成论文附录 A 说明程序由动作及顺序描述归纳，随后给生成器步骤、错误行为、解释和原因。短证据：“summarized the annotated steps and their order”。[论文附录 A](https://arxiv.org/html/2608.24134v1)

评测实现也确实将完整任务文字提供给回答模型：`full_question` 在 Question 前拼接 `Task Procedure`，再发送视频路径与起止时间。**你的判断正确，流程规范是模型输入的一部分。** [代码 L680–698](https://github.com/z1oong/EgoErrorVQA/blob/5403cdd05e007b01c88448587c1a1803a27266e2/src/green_agent/agent.py#L680)

但发布形式是 **一份通用玩具车流程文字**，不是为每个玩具型号提供一份机器可执行的完整 DAG。内容大意是先连接基础部件，再门/驾驶室/车顶等，并给出各型号可能有的补充组件；还包含因频繁出现而强调或重复的步骤叙述。不能把这段通用文字当作适用于所有车型的精确工艺图，更不能把其中全部顺序迁移到角磨机。[procedure.json](https://github.com/z1oong/EgoErrorVQA/blob/5403cdd05e007b01c88448587c1a1803a27266e2/data/json/procedure.json)

原题也不是每个答案都能由源备注严密推出。例如某 wrong order 例的答案改成交换“底座/底盘”的主宾关系，这与时间顺序并不等价；另有“牢固、用力”等细节无法仅由 correct 标签验证。本次没有观看 Assembly101 原视频，因此不判定这些答案一定错误，只记录：源标签不足以单独验证这类增补。借鉴题型和输入组织，同时保留自己的证据检查。

## 5. IMPACT 能否生成安装完成与顺序题

可以，而且需要升级选段单位和输入，而不只是修改问句。

| 所需能力 | IMPACT 已有资产 | 仍需处理 |
|---|---|---|
| 当前动作/阶段/错误 | TAS-B 动作、对象、手、phase、六属性 | 通常没有 Assembly101 式显式 receiver；不凭 noun 猜安装到哪里 |
| 安装完成和当前状态 | ASR 92 front 视频、17 部件状态；PSR 完成事件 | 与动作/组件实例对应；选取完成前后窗口 |
| 实际先后 | TAS-B/TAS-S 时序、PSR 事件时间 | 跨窗口覆盖，处理并行手、重试、初态及后续拆除 |
| 正常规范顺序 | 正常流程说明与有来源的前置关系；已有挖掘图可参考 | 型号/拆装方向、关系可信度、训练/测试隔离 |
| ego 视频中的状态真值 | front 状态标注加多视角媒体 | 必须先验证 front–ego 同步及对应关系，不能直接搬帧号 |

ASR/PSR 适合支持这类题：官方任务说明明确说 PSR 预测 “completed procedure steps”，ASR 预测组件安装状态。[BENCHMARK.md](https://github.com/Kratos-Wen/IMPACT/blob/4fed5faa5f05f7aece55712e458defa1f372b248/docs/BENCHMARK.md)

本次额外核查 ASR：92 条执行（装/拆各46），1457 状态记录，3231 个组件状态变化。0→1 为39、-1→1 为739；这是组件记录的变化，不是778个独立、已目视核验的安装/恢复视频。多个组件可能同一帧同步改变。具体例 AL07EJ17_Reassembly_A_002_front 的齿轮箱、轴、锥齿轮和 M6 螺母在 frame653 为 -1，到982为1，对应21.767–32.733秒（标注30fps）。可以据状态问“32.733秒时是否已正确安装”，但不能由此独立确定每个组件的实际安装先后或安装接收部件。

还发现该例653和982帧的双手 TAS-B phase 均为 normal。因此 **ASR 的 -1→1 不可自动叫作 PPR 恢复**；官方称 -1 为 misassembled，但这里的状态级含义与动作级异常并不一一对应。不能统计出739个“修复错误”或据此编造先前错误原因。详见 [状态核查](question_taxonomy/impact_state_support.json) 与 [逐组件变化](question_taxonomy/impact_component_transitions.jsonl)。

已有 procedure_graph.json 实测53节点、102边，无环；元数据写 “Edges are robust prerequisites mined from data”，基于92视频挖掘。它是候选关系，含 install/recover/remove 等事件节点，并非逐型号人工确认的完整正常流程。[发布图](https://github.com/Kratos-Wen/IMPACT/blob/4fed5faa5f05f7aece55712e458defa1f372b248/tasks/PSR/gemini_3_1_pro/configs/procedure_graph.json)

因此给模型“完整规范文字＋图”是正确方向，但必须保存来源和适用条件：正常文本负责解释各步骤，图负责必要依赖，实际事件/状态负责是否执行。A→C、B→C 可以允许 A/B 任意先后；只看某一条拓扑序不能判另一条合法路径为错序。缺边也不证明可互换，除非规范已完整覆盖该关系。ASR 状态1不等于视频中可以看出螺丝扭矩等物理指标。

## 6. 已完成的 prompt 设计

新增 [v10 输入契约](v10_input_contract.md)，提示在 prompts/impact_qa/v10：procedure（规范整理）、plan（有证据条件的题型选择）、generate（安装/完成/顺序等问题）、review（来源支持与视觉可见性分开检查）。这些是设计稿，尚未运行 v10。

要点：完整 procedure 和图重新进入输入；安装类优先考虑“X→Y 是否正确安装”和“截止目标时刻是否完成”；顺序类需要前置条件和实际时间线；以粗步骤/完成事件窗口补足原来0.6–几秒的微动作输入。允许简短的 Yes/No 加解释，不要求长 CoT。公开规范可以提供给被测模型，测试执行的错误标签、ASR真值、参考答案不能进入它的输入。下一轮先补齐规范和映射输入并抽取新开发窗口，再做提示实验，不能用已有20个短动作的输出证明完成/顺序能力。

验证：两个新增统计脚本语法通过、3560行与来源数校验通过，规则及抽样边界实例已阅读。主题计数仍为规则编码，不声称逐条人工语义审核；状态统计不称作视频核验。web 工具仍报404，本轮使用已验证的官方提交/PDF本地快照，没有把检索失败当作缺少论文证据。
